# Issue 看板阶段与旧版布局

看板默认展示顶层 Issue，卡片读整棵树的工作事实。CLI 仍可分页查询全部或单个 Chat 的 Issue。Issue Chat 保留父子留言、PR 与执行详情的入口。

Router 可以登记一份待安排 Issue，沿原 Chat 保存目标和执行要求。记录时没有执行 Task。用户要求开工时，Router 或 CLI 沿原 Issue 激活一次，复用已有任务派发机制。直接交代现在做的工作继续即时派发。重复调用沿原 Issue 和操作查证。

按业务终态、待安排、实际运行、可安排工作和登记等待的顺序分列。已完成和已取消沿 Owner 的业务结算。开放的 Issue 树有任一实际 Run 即为进行中。停妥以后，有可安排的 Task 或待处理的原输入时进入待推进；整棵树只等已登记的事实或回复时进入等待中。未结案且缺少明确等待的 Issue 仍在待推进。领取、容量与工作区独占沿已有执行契约。

需要用户处理的已发布 Attention 在卡片显示「待你决定」，点击回到原 Chat。用户检查属于这类决策。普通审阅按实际运行或等待分列。结案后的卡片可以显示仍在收尾的子执行。

视觉以旧 Tend 的桌面和窄屏看板为基准。桌面使用紧凑六列、状态圆点、计数、浅色列底与细边框卡片，保留每列的空状态。「已取消」可收起为窄列。窄屏采用横向状态标签并一次显示一列。卡片沿用顶层标题与短元数据，直接打开 Issue，对用户的决策保留明确入口。

使用现有 App Server fixture 覆盖记录、重复提交、原 Issue 准入、子 Run 实际运行与停妥、待推进与等待优先级、Attention 和终态。复跑看板 PR 和真实浏览器入口，检查列、卡片、移动标签及空状态。在旧址更新 Server 和 Web 后再次验证。
