# 维护建议首期（#139）

在桌面及窄屏提供常驻「维护建议」入口，与通知、飞书建议和工作看板分开。参考旧 Tend `MaintenanceCase` 的来源、异常代码、观察时间和证据指纹。建议是观测记录，不是工作项。首期没有自动调查、修复、部署、工作派发或业务状态变更。

## 实际探测来源

| 原对象／异常类型 | 判定为异常的证据 | 消失或恢复的证据 |
| --- | --- | --- |
| 已配置的 Tend NG 飞书扫描身份／`feishu_scan_stalled` | 有成功扫描基线，但扫描 checkpoint 已连续 30 分钟无提交推进。用最后一次实际推进的提交时间，不能用游标本身的年龄、进程存活或 `running` 判断。迁移前仅以曾成功提交的时间为基线。 | 新窗口仍在补扫时，记为当前未观察到停滞。只有已提交的完整扫描窗口越过异常游标、追至扫描轮次目标且近期完成，才记为证实恢复。缺配置、身份或观测行时不判恢复。 |
| 原 Task／`task_execution_failed` | 所属 Issue 及祖先仍开放、未退回待安排，Task 当前为 `failed`，其当前 Assignment 有 Server 已接收的真实停止证据，最近 Run 的 outcome 为 `failed`。不按耗时、离线、普通排队、等待、未确认执行过程或 PR/CI 状态猜测故障。 | 后续重新排队、等待、运行、停止或 Issue 关闭只代表当前不再观察到这个失败。只有原 Task 后续不同 Run 的正向停止证据和 Task `completed` 一起成立才证实恢复。Task 完成不代替 Issue 或交付验收。 |

LDD 无 Tend NG 采集链，首期不连 LDD 或读取线上日志。用相同的八天停扫形态做合成对照，验证飞书的旧 `running` 不能掩盖停滞，逐窗提交的积压不能触发误报。也不覆盖从未成功过的扫描、瞬时失败、缺失的外部观测或未同步的 Runner 行为。

## 持久化和处置

- Server 按 `(anomaly_type, subject_id)` 保留单一建议及稳定深链。定时探测独立于 HTTP 读，按有界批处理 Task 并单独检查已配置的飞书扫描记录。记录首次／最近异常观察、最近状态变化及证据版本。重复观察只刷新异常观察时间，不刷新证据版本。进展、复发、仅消失和已证实恢复更新原建议。原异常证据与后续观察分别保留。观察不到的数据不冒充正常。
- 人工忽略绑定已见的证据版本，重复观测不会重新提醒。证据改变后同一建议重新显示。用户可以查看并撤销忽略。附入讨论或转给原主 Chat 时固定当前所选版本，使用服务端生成的自包含说明，包含影响、证据、已知／未知、时点和回链。原 Task 可追溯到主 Chat 时额外提供原话题入口。
- 新建讨论、附入既有讨论、转给原主 Chat 都是显式操作。独立讨论和主 Chat 以「维护建议」署名展示用户手动加入的说明，不产生 Router／Discussion 待执行输入。用户可在目的地另行回复并决定是否调查。相同建议版本和目的地重放不重复入账，旧版本转载保留原文。新增异常类型可实现自己的观测和证明规则，本次无自动动作注册。
- Web 与 CLI 使用同一用户 API，Cookie 写沿现有同源校验。列表固定键分页，刷新不会写库或触发探测。具体取样间隔、复发判断及不覆盖项一并记录在最终说明。

首轮审阅补充两条验收边界。补扫的运行阶段与上次已确认的故障原因分别保存，尚未提交窗口的重试及相同失败不改变证据版本或撤销忽略。浏览器提交分享后若未取得明确回执，在当前页面保留当次版本、动作和目标，证据更新后仍可手动重放；查看并确认新版是另一项操作。用真实本机 Server 暂停一次同错重试，并在 Chromium 截断实际已提交的三种分享回执，验证证据更新后的原回执、说明数量和原业务状态。

## 验收与交付

1. Rust fixture 验证重复证据、更新时间、证据版本、忽略及复发、正常排队与等待、补扫推进、现象消失、正向恢复和重启持久性。
2. 用本机隔离 Server、SQLite 和合成源观测走生产探测与 API，不要操作线上数据。验证已鉴权和未鉴权、只读不触发、副作用边界、同一版本重放、新旧说明快照和原业务状态未变。浏览器从桌面及 390px 窄屏访问真实静态构建和本机 API，保存实际渲染图并覆盖手动处置与深链。
3. 冻结依赖、格式、定向 Rust/进程 fixture 和 Web 类型、lint、测试、构建。按仓库门槛审阅确切候选，直接快进推送 `origin/main`，核对远端完整 SHA。合入即交付，不部署、不等待未要求的 CI 或出包终点。

## 第二轮审阅增量

- 飞书重启只更新扫描阶段。公共状态仍显示「扫描中断」及补扫提示，维护建议只比较已提交的进展和已确认的故障原因，旧版残留的阶段标记也不作为故障原因。用真实本机 Server 暂停补扫，分别检查没有故障原因的已忽略建议在重启前后是否保留原证据与版本，以及随后真实失败是否只更新同一建议。
- 分享确认后，未结清的原版本、动作和目标由维护建议页面持有，不由详情或草稿表单持有。用户可关闭详情或切换分类，页面仍提供显式原样重试。在收到回执或服务端明确拒绝前，不能提交另一份说明。确认前的草稿仍可取消。用 Chromium 验证截断已提交回执、关闭详情与切换分类后的查证，并验证未抵达 Server 的旧请求在重放收到 409 后才可独立确认新版。范围是当前打开的维护页面，不新增跨刷新或跨标签的客户端持久化。

## 第三轮审阅增量

- 提示覆盖实际续扫阶段。重启后的短积压在身份核验及窗口尚未提交时，公开 API 仍返回 `running/interrupted`。长积压进入分段追赶后显示 `running/catching_up`，提交成功或出现新的确认失败后显示实际结果。用独立的内部续扫阶段承载提示，不改变原有 `gap` 中的故障证据或持久化结构。真实本机 Server 用一小时与八天旧检查点分别暂停重启后的搜索，验证公开提示、检查点、最后成功时间及已忽略证据，随后分别放行成功与失败，验证提示和建议按真实结果更新。
