# 子 Issue 留言唤醒试跑

一期先按已定规则将子 Issue 的显式留言、业务状态变化和新交付沿原委派关系送到上级并请求唤醒。普通留言触发模型回合的成本留待试跑观察。父 Issue Chat 从持久的原留言合并阅读。 [父子 Issue 的等待与唤醒](../task-lifecycle.md#父子-issue-的等待与唤醒)

## 固定输入回放

用一台 Runner、一个 slot 和固定时钟，回放同一子 Run 内的多条留言、每轮留言后释放 slot，以及两级上级收到普通回复和请求上级决策的上报。固定输入包含同一原记录的重传。每个上级按原事件身份收件，已有待运行请求时继续入队，有 slot 时按一轮消费当前批次。回放中的 Agent 回合时长和哪些输入需要上级行动由 fixture 指定。

对照两种唤醒策略。第一种按当前规则，显式留言、上报、状态变化和交付均请求唤醒。第二种保留相同收件，普通留言随下一次上级处理时读取，单独请求唤醒的来源为显式上报、状态变化和交付。两种策略共用一个调度实现，记录唯一收件数、唤醒请求数、实际启动的回合、只消费普通留言的回合，以及需上级行动的输入从送达至消费的时间。

旧 Tend 在子 Issue 关闭或取消时通过 `issue.child_result` 向直接父级送达，并按接收对象合并待处理输入。将旧代码作为合并规则参考，回放使用 Tend NG 的 Issue 树与唤醒范围。 [旧子 Issue 终态触发](https://github.com/GhostFlying/tend/blob/83bc15ae/internal/app/app.go#L518-L527) · [旧父级送达](https://github.com/GhostFlying/tend/blob/83bc15ae/internal/app/hosted_assignment.go#L302-L322) · [旧待处理批次](https://github.com/GhostFlying/tend/blob/83bc15ae/internal/app/background_queue.go#L86-L95)

试验放在 `spikes/child-issue-wake/`，在开发容器使用 Python 标准库运行。回放从固定输入起步，结果用于确认可能增加回合的时序。实际用量和上级处理结果在产品运行后沿持久输入与原生回合核对。

## 回放结果

在禁用外网的 Linux 开发容器运行，固定每个上级回合占用 slot 30 秒。本机可用的旧用量快照中唤醒表为空，历史参照使用旧 Tend 的触发与批次源码。

| 场景 | 两种策略的持久投递数 | 每条留言也唤醒时的回合数 | 仅上报、状态和交付唤醒时的回合数 | 差额中的回合内容 |
| --- | ---: | ---: | ---: | --- |
| 子任务持续占用唯一 slot，六条留言后交付 | 8 | 1 | 1 | 六条留言和终态事实一起处理。 |
| 六条普通留言，每次发完都有空闲 slot | 8 | 7 | 1 | 六轮只消费一条普通留言。最后一轮处理交付与结案。 |
| 两级上级，收到两条普通回复、一次上报及终态事实 | 10 | 8 | 4 | 四轮只消费普通回复。显式上报和交付各送两级。 |

两个策略下，fixture 标注为需处理的输入最长等待分别为 0 秒、0 秒、30 秒，按三个场景顺序相同。第一组重复递送的结案仍只按原事件入队一次。只消费普通留言的回合属于这组固定场景给出的分类，实际收益要沿真实回合和处理结果核对。

维持当前规则试跑。上级排队期间以同一待运行请求承接新增输入。产品运行后，按原事件身份把留言、上报、状态和交付同实际启动的回合关联起来，优先抽查仅由普通留言拉起的回合是否有上级决策、协调动作或用户回报。第二种策略留作对照，普通留言仍可从合并时间线和下一轮输入读取。

python3 spikes/child-issue-wake/replay.py
