# 讨论引用变化与原生线程接续

## 目标与边界

空白讨论附加、删除或替换仓库及同机 Issue worktree 后，仍接续同一 Chat 已有的精确 Codex thread ID。下个回合只读本轮实际选择的目录，不再读被撤销的目录。保留独立 App Server、无写入、无网络、环境清理和定向只读工具，不改主 Router、Runner 协议或 Web。验收到 main，不部署。

## 方案

- 从讨论的持久 thread 绑定移除附件范围依赖，延续先前已带范围哈希保存的绑定。先恢复已知原生尝试，再接续当前绑定。旧版可能在重试耗尽时只清除绑定。遇到此状态时，按输入及尝试顺序从新到旧查询同一讨论记录中的原生 ID，去重后按序续用，并在成功时恢复绑定。只有原生 resume 明确报告历史缺失或不可用，才以原引用和近期持久历史启动替代 thread。
- 保持只读 profile 定义稳定，使用 `:workspace_roots` 绑定本轮 canonical roots。启动、续用和回合启动都发送同一组 roots，启动和续用核对 App Server 返回的 profile、安全设置和 roots。撤销目录只影响后续实际文件访问，不能抹除先前已读的内容。
- 保持工作和 Router 回合的原有请求格式。更新 Chat 与工具契约。

## 验证

定向 Rust 测试和锁定 release 构建。固定 App Server fixture 检查同一 thread ID、每轮请求、引用范围、已保存绑定接续、旧版清除绑定后从原尝试找回线程、原生历史确实缺失时的历史回放。真实 App Server 使用独立临时 Codex home、合成文件和本地固定模型响应执行原生 shell，核对跨进程续用的 ID、切换前后读权限、写入、联网和凭据隔离。若实测不能同时保留原 ID 并撤权，保留证据并等待决定，不提交。
