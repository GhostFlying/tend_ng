# Issue 标题与改名历史实施计划

## 交付

在独立 Issue 实施已确认的标题契约。Router 创建时用可辨认的工作与结果作标题。已领取的 Owner 可显式修正自己 Issue 的标题，单用户可由 CLI/API 改名。Web 显示当前标题和只读改名历史。源码按仓库门禁独立审阅并合入 `origin/main`，本项不部署。

## 实施顺序

1. 按 [标题契约](../task-lifecycle.md#issue-标题与改名历史) 增加 Server 标题日志与用户事务。实现有界的同 Issue 历史读取，保留原请求、Assignment 合同、消息、链接、状态和工作目标。
2. 复用 Runner 原生工具调用、持久操作和 outbox。Owner 工具只收标题，Issue 从本地 Run 写入原操作。Server 沿原 Runner、Assignment、Task、Run 和已领取 Owner 校验。给增量与全量路径共用的操作增加可选能力声明并处理混合版本。
3. 更新 Router 创建指引和各 Owner 角色指引。添加 Bearer 用户 API、CLI 及 Issue 详情中的只读改名历史。沿现有游标分批读取较早的事件，不把它们混入会投递的 Issue 对话。
4. 用真实的隔离 Server、Runner、CLI 和固定 App Server fixture 验证领取、越权失败、断线受理、重启补传、丢 ACK、幂等以及副作用。检查旧/新发布两种组合、历史快照和当前标题的区别。用 Chromium 在桌面和窄屏打开真实 fixture 页面，验证无编辑入口并保存最终渲染。
5. 定向运行 Rust、Web 和相关主链回归，对精确提交安排独立审阅。确认实际审核候选与远端基线，快进推送后读取完整远端 SHA 和当时的 CI 事实，不将构建或部署列为本项停点。

## 独立审阅后的同步边界

首轮审阅复现了 Runner 持久受理超限标题后反复收到 HTTP 413。改名在工具、用户 API 和 Server 同步入口共享 1024 UTF-8 字节的规范化上限。上限约束单个标题的传输量，不限制改名次数。合法的改名与其他业务记录组成的包若仍超出 256 KiB，增量和全量只发送可放入当前请求的有序记录前缀。增量依原回执移除前缀，全量只越过本次实际发送并成功结算的记录。单条非改名记录本身超过传输上限不在本项修复范围。

补充隔离回归覆盖原 256 KiB 工具调用不入账、规范化后按字节拒绝多字节超限、合法边界、混合大批次原序、后续合法关闭和全量重放。
